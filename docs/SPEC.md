## Core Principles

- **Multi-chain**: минимум TON (native + Jettons), Tron (TRC20 USDT), Ethereum (ERC20 USDT), BSC (BEP20 USDT).
- **Non-custodial**: приватные ключи существуют только на устройстве пользователя. Backend, арбитры и администраторы контракта не могут перевести средства пользователя на произвольный адрес.
- **Fail-safe**: если данные для проверки безопасности недоступны (курсы, RPC, blacklist), приложение ведёт себя так, как будто проверка провалилась, а не пропускает её.

## Mobile Apps: iOS (Crypto)

- WalletCore: деривация ключей для всех сетей, включая TON (тот же код, что на Android, чтобы адреса гарантированно совпадали), а также транзакции Tron, Ethereum и BSC.
- TonSwift: контракты TON-кошелька, сообщения, Jetton transfer.
- BEP20 работает на том же EVM-стеке, что и ETH; различаются только `chainId` и RPC.

## Mobile Apps: Android (Crypto)

- WalletCore для деривации и всех EVM-цепей, включая BSC.

## Onboarding

### Derivation Paths

Мультичейн-аккаунты выводятся из одного BIP39 seed:

| Сеть | Кривая | Путь | Формат адреса |
|---|---|---|---|
| TON | ed25519 (SLIP-10) | `m/44'/607'/0'` | wallet v4r2, `UQ…`/`EQ…` |
| Tron | secp256k1 | `m/44'/195'/0'/0/0` | Base58Check, `T…` |
| Ethereum | secp256k1 | `m/44'/60'/0'/0/0` | `0x…`, EIP-55 |
| BSC | secp256k1 | `m/44'/60'/0'/0/0` | тот же путь, что у ETH: **один адрес работает в обеих EVM-сетях** |

Так как у ETH и BSC общий ключ, каждая EVM-транзакция подписывается строго с EIP-155 `chainId` (Ethereum `1`, BSC `56`). Подпись legacy-транзакций без chainId запрещена: такую транзакцию можно воспроизвести в другой сети.

### Совместимость seed и импорт

- **Экспорт.** Seed — стандартная BIP39-фраза. По всем сетям она совместима с кошельками на WalletCore и BIP44 (Trust Wallet, Ledger). Нативные TON-кошельки (Tonkeeper, MyTonWallet) используют собственную схему мнемоники и для этой фразы покажут другой TON-адрес или не примут её. На экране экспорта seed это прямо написано.
- **Импорт BIP39-фразы.** Создаются аккаунты всех сетей. Для TON баланс проверяется на версиях v3r2, v4r2 и W5. Если средства нашлись не на v4r2, пользователю предлагается перевести их на основной адрес.
- **Импорт TON-native мнемоники (24 слова от Tonkeeper и т.п.).** Создаётся только TON-аккаунт, другие сети для него недоступны, и в интерфейсе это видно.
- Если 24 слова одновременно валидны и как BIP39, и как TON-мнемоника, приложение спрашивает, из какого кошелька фраза, и не выбирает молча.

Проверено: EIP-55 checksum обоих EVM-адресов, Base58Check для TRC20 (version byte `0x41`) и CRC16 TON-адреса (bounceable, mainnet, workchain 0).

**Важно про BEP20 USDT:** у него 18 decimals (как у BNB), а не 6, как у TRC20/ERC20. Код, скопированный с логики других сетей, на этом сломается. Decimals задаются только через реестр ниже и сверяются с on-chain `decimals()`.

### Правила работы с суммами

- Суммы хранятся и передаются только в минимальных единицах как целые числа (`BigInt` / `BigInteger` / `Decimal`; в БД `NUMERIC(78,0)`) вместе с `asset_id`. `float`/`double` запрещены.
- Перевод «человеческих» сумм в минимальные единицы и обратно идёт только через реестр выше. Ввод с большим числом знаков после запятой, чем decimals ассета, отклоняется, а не округляется.
- При старте backend сверяет decimals из реестра с on-chain `decimals()` (для Jetton с метаданными). Если значения расходятся, сервис не стартует.
- Любой денежный лимит в долларах (в приложении, на backend, в контракте) задаётся отдельно для каждого ассета в его единицах. Пример лимита $10 000:

  | Ассет | Значение в контракте |
  |---|---|
  | USDT_TON, USDT_TRC20, USDT_ERC20 | `10_000 * 10^6` = `10000000000` |
  | USDT_BEP20 | `10_000 * 10^18` = `10000000000000000000000` |

## Gas Reserve Logic

Резерв native-токена под газ считается **перед каждой отправкой** по формуле: оценка стоимости транзакции × 1.2. Фиксированные значения ниже используются только как fallback, если оценку получить не удалось, и как нижняя граница при показе предупреждения «пополните баланс».

| Сеть | Как оценивается | Fallback-резерв |
|---|---|---|
| TON | эмуляция сообщения (Toncenter `estimateFee` / emulation API). Jetton transfer прикладывает ~0.05 TON (излишек возвращается), комиссия кошелька сверху | 0.1 TON |
| Tron (USDT TRC20) | `triggerconstantcontract` / `estimateenergy` × текущая цена energy + bandwidth. Перевод на адрес без USDT стоит примерно вдвое больше energy (~130k против ~65k) | 30 TRX |
| Ethereum (USDT ERC20) | `eth_estimateGas` × `maxFeePerGas` | 0.003 ETH |
| BSC (USDT BEP20) | `eth_estimateGas` × `gasPrice` | 0.001 BNB |

- Для Tron поддерживается energy rental за счёт спонсора. Если спонсор доступен, требование к TRX снижается до bandwidth.
- Кнопка «Max» для native-актива вычитает резерв.
- Если native-баланса не хватает на газ, отправка токена блокируется до экрана подтверждения, а пользователь видит, сколько и какого токена нужно докупить.

1. Явно показывать выбранную сеть на каждом экране.
2. Предупреждать при отправке USDT: «Убедитесь, что получатель поддерживает USDT в сети BEP20» (название сети подставляется).
3. Проверять активность адреса получателя в обеих EVM-сетях и предупреждать, если в выбранной сети её нет, а в другой есть (подробно в разделе 2 «Network Mismatch Protection»).

## Security & Validation: КРИТИЧЕСКИЙ ПРИОРИТЕТ

Non-custodial не значит «безопасно по умолчанию». Атакуют не только ключи, но и UX, буфер обмена, через фишинг и MITM, а также бэкенд с данными пользователей (адреса, payment methods, суммы).

### 1. Address Validation (жёсткая проверка перед любой отправкой)

**TON-адреса:**

```swift
func validateTonAddress(_ address: String) -> Bool {
    // Два формата: EQ.../UQ... (user-friendly base64url) или raw 0:...
    guard let parsed = try? TonSwift.Address.parse(address) else { return false }
    // Checksum (CRC16) есть только у user-friendly формата, у raw "0:<hex>" его нет
    return true
}
```

- Адреса с флагом testnet (`kQ…`/`0Q…`, бит `0x80` в tag) в mainnet отклоняются.
- Raw-формат `0:<hex>` не содержит checksum, и опечатка в нём проходит парсинг. Такой адрес перед подтверждением показывается в user-friendly форме, и пользователь подтверждает его отдельно.
- Native TON на незадеплоенный (uninit) кошелёк отправляется как non-bounceable (`UQ…`), иначе перевод вернётся отправителю.

**EVM-адреса (ETH / BSC):**

- 42 символа, префикс `0x`, только hex.
- EIP-55: адрес целиком в нижнем или целиком в верхнем регистре принимается без checksum. Адрес в смешанном регистре обязан пройти проверку checksum, иначе отклоняется.
- Отклонять `0x0000000000000000000000000000000000000000` и известные burn-адреса.

**Tron-адреса:**

- Префикс `T`, длина 34, Base58Check, version byte `0x41`.
- Проверка через WalletCore `AnyAddress.isValid(string:coin: .tron)` (mobile) или `tronweb.isAddress()` (JS). Вручную: Base58 decode + сравнение с первыми 4 байтами двойного SHA-256.

**Общие правила:**

- Проверка выполняется ДО показа экрана подтверждения, а не после.
- При вставке из буфера адрес сразу валидируется, ошибка подсвечивается красным.
- QR-скан: содержимое валидируется до заполнения полей. Если в QR (EIP-681, `ton://transfer`, TRON URI) указана сеть или chainId, они должны совпадать с выбранной сетью, иначе ошибка.
- Address book (сохранённые получатели) хранит адрес вместе с меткой сети. Адрес из address book нельзя использовать в другой сети без отдельного подтверждения.

### 2. Network Mismatch Protection

Главная причина потерь USDT: отправка в неправильной сети.

**Правила:**

- Сеть выбирается ДО адреса, а не после.
- Смена сети очищает поле адреса.
- Для адреса `0x…` показывается предупреждение: «Это EVM-адрес. Убедитесь, что получатель принимает USDT в сети {ERC20|BEP20}. USDT, отправленный в неправильной сети, будет потерян.»
- **On-chain проверка EVM-адреса** перед экраном подтверждения. Запросы идут в обе сети, Ethereum и BSC, параллельно, с таймаутом 3 секунды:
  - `eth_getTransactionCount` и `eth_getCode` по адресу;
  - наличие входящих переводов USDT через индексатор (Etherscan API V2 с `chainid` 1 / 56 или собственный индексатор).

  | Результат | Действие |
  |---|---|
  | В выбранной сети есть активность | без дополнительных предупреждений |
  | В выбранной сети активности нет, в другой есть | жёлтое предупреждение: «Этот адрес использовался только в сети {X}. Переключить сеть?» |
  | В другой сети по адресу контракт, в выбранной нет (Safe-мультисиг и т.п.) | красное предупреждение: «Контракт существует только в сети {X}. Средства, отправленные в {Y}, могут быть невозвратны». Отправка только после ввода суммы повторно |
  | Проверка не ответила за таймаут | считается как «активности нет», показывается жёлтое предупреждение |

- Для сумм больше $100 обязателен чекбокс «Я подтверждаю, что сеть выбрана правильно».

### 3. Private Key / Seed Storage

**iOS:**

```swift
// 1. P-256 ключ в Secure Enclave. Приватный ключ не покидает SE,
//    для операций с ним нужна биометрия текущего набора отпечатков/лица.
guard let access = SecAccessControlCreateWithFlags(
    nil,
    kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,
    [.privateKeyUsage, .biometryCurrentSet],
    nil
) else { throw WalletError.accessControl }

let keyAttributes: [String: Any] = [
    kSecAttrKeyType as String: kSecAttrKeyTypeECSECPrimeRandom,   // SE поддерживает только P-256
    kSecAttrKeySizeInBits as String: 256,
    kSecAttrTokenID as String: kSecAttrTokenIDSecureEnclave,
    kSecPrivateKeyAttrs as String: [
        kSecAttrIsPermanent as String: true,
        kSecAttrApplicationTag as String: Data("wallet.seed.encryption".utf8),
        kSecAttrAccessControl as String: access,
    ],
]
var error: Unmanaged<CFError>?
guard let seKey = SecKeyCreateRandomKey(keyAttributes as CFDictionary, &error),
      let publicKey = SecKeyCopyPublicKey(seKey) else {
    throw error?.takeRetainedValue() ?? WalletError.keyGeneration
}

// 2. ECIES: шифрование публичным ключом проходит без биометрии,
//    расшифровка (SecKeyCreateDecryptedData с seKey) требует Face ID / Touch ID.
let algorithm: SecKeyAlgorithm = .eciesEncryptionCofactorVariableIVX963SHA256AESGCM
guard SecKeyIsAlgorithmSupported(seKey, .decrypt, algorithm),
      let encryptedSeed = SecKeyCreateEncryptedData(
          publicKey, algorithm, seedData as CFData, &error
      ) as Data? else {
    throw WalletError.encryption
}

// 3. В Keychain кладём только шифротекст. Используется ЛИБО kSecAttrAccessible,
//    ЛИБО kSecAttrAccessControl, оба сразу задавать нельзя. Биометрию уже даёт ключ SE.
let query: [String: Any] = [
    kSecClass as String: kSecClassGenericPassword,
    kSecAttrService as String: "pmrwallet.seed",
    kSecAttrAccount as String: "primary",
    kSecValueData as String: encryptedSeed,
    kSecAttrAccessible as String: kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly,
]
let status = SecItemAdd(query as CFDictionary, nil)
guard status == errSecSuccess else { throw WalletError.keychain(status) }
```

**Android:**

```kotlin
// Android Keystore + BiometricPrompt для разблокировки. minSdk 30 (setUserAuthenticationParameters).
```

**Правила хранения:**

- Seed НИКОГДА не лежит в памяти в plaintext дольше необходимого: после использования буфер обнуляется.
- `String` для seed запрещён, только `CharArray`/`Data` с явным обнулением.
- Если биометрия перерегистрирована, ключ инвалидируется. Восстановить доступ можно только вводом seed-фразы, этот сценарий описан в онбординге.
- Экран показа seed при создании защищается от снимков:
  - iOS: системно запретить скриншоты нельзя. Запись экрана и AirPlay детектируются через `UIScreen.main.isCaptured`: seed скрывается overlay'ем. Скриншот детектируется через `UIApplication.userDidTakeScreenshotNotification`: пользователь получает предупреждение, что seed скомпрометирован, и предложение создать новый кошелёк.
  - Android: `WindowManager.LayoutParams.FLAG_SECURE`.
- Экспорт seed каждый раз требует биометрию, даже если приложение недавно разблокировали.
- Автоблокировка: после 1 минуты простоя нужна биометрия.
- В app switcher вместо содержимого показывается заглушка: iOS — overlay в `sceneWillResignActive`, Android — `FLAG_SECURE`.

### 4. Clipboard Protection

Классическая атака: malware подменяет адрес в буфере обмена на свой.

- При вставке адреса показывается превью первых и последних 6 символов и запрашивается подтверждение.
- Детекция подмены для данных, скопированных внутри приложения (свои адреса, address book, история). Приложение запоминает скопированное значение; если при вставке значение отличается, показывается alert. Что пользователь копировал в других приложениях, приложение знать не может, поэтому для внешних адресов защита — это превью и подтверждение.
- Свои адреса не остаются в буфере после копирования:

  ```swift
  import UniformTypeIdentifiers

  UIPasteboard.general.setItems(
      [[UTType.plainText.identifier: address]],
      options: [
          .localOnly: true,                                   // не уходит в Universal Clipboard
          .expirationDate: Date().addingTimeInterval(60),
      ]
  )
  ```

  Android 13+: при копировании адреса в `ClipDescription` выставляется `EXTRA_IS_SENSITIVE`.
- Для сумм больше $500 вставка адреса отключена: только QR, address book или ручной ввод.

### 5. Transaction Signing Flow

**Обязательные экраны перед подписью:**

1. Получатель: полный адрес, не сокращённый
2. Сумма с эквивалентом в USD
3. Сеть: крупно, цветной бейдж с текстом
4. Комиссия в native-токене + USD
5. Итог
6. Подтверждение биометрией

**Детекция подозрительных транзакций:**

- Первая отправка на этот адрес: предупреждение «Вы ещё не отправляли на этот адрес».
- Отправка больше 50% баланса требует повторного подтверждения.
- Адрес в scam-blacklist (ведётся на бэкенде, обновляется через API) — отправка блокируется.
- **Address poisoning:** адрес совпадает с адресом из истории по первым и последним 4+ символам, но отличается в середине — красное предупреждение. Входящие переводы на 0 и пыль от неизвестных адресов скрываются из истории по умолчанию.
- Необычный gas price или комиссия (больше 3× от медианы за последний час) — предупреждение.

**Подтверждение результата:**

- Успех отправки токена определяется по статусу receipt (`status == 1`) и событию `Transfer` в контракте из реестра, а не по return value `transfer()`. USDT ERC20 не возвращает `bool`.
- Транзакция считается завершённой после финализации:

  | Сеть | Финализация |
  |---|---|
  | Ethereum | `finalized` block tag |
  | BSC | 15 блоков |
  | Tron | solidified block |
  | TON | транзакция в masterchain-подтверждённом блоке |

  До этого в интерфейсе статус «в обработке».

### 6. Backend Security

**Защита API:**

- Только HTTPS (TLS 1.2+), HSTS preload.
- **Certificate pinning** в мобильных приложениях:
  - Пинится SHA-256 от SPKI (публичного ключа), а не сертификат целиком.
  - На Cloudflare загружается собственный сертификат (Custom Certificate) с ключом, который сгенерировали мы. Edge-сертификаты Cloudflare не пинятся: Cloudflare их ротирует, и приложение сломается. Возможность загрузить свой сертификат — обязательное требование к плану Cloudflare.
  - В приложение зашиты 3 пина: текущий ключ + 2 резервных. Резервные ключи сгенерированы заранее и хранятся офлайн в разных местах.
  - Ротация: сертификат перевыпускается на тот же или на резервный ключ. Новый резервный пин добавляется в приложение за один релизный цикл до использования.
  - Несовпадение пина = запрос не отправляется, пользователь видит ошибку соединения. Отключить пиннинг из приложения нельзя.
- JWT access token на 15 минут + refresh token на 30 дней:
  - ротация refresh token при каждом использовании;
  - повторное использование уже ротированного refresh token отзывает всё семейство токенов этой сессии (признак кражи), и пользователь заново проходит вход;
  - refresh token привязан к устройству (device ID + ключ устройства).
- Rate limiting (Redis):
  - 100 req/min на IP для чтения
  - 20 req/min на пользователя для записи
  - 5 req/min на auth-эндпоинты
  - Создание ордеров:
    - 3 в час на пользователя и 3 в час на устройство (device fingerprint);
    - на IP мягкий лимит 30 в час: при превышении требуется captcha, а не блокировка. У мобильных операторов CGNAT, и через один IP выходят тысячи абонентов.
- Idempotency keys на POST (защита от двойных ордеров).

**Защита данных пользователей:**

- PII в БД (payment methods, telegram username) шифруется на уровне приложения: AES-256-GCM, ключи в Vault, envelope encryption. `pgcrypto` не используется: ключ при нём проходит через SQL и может попасть в логи БД.
- В логах НЕТ адресов, сумм, telegram_id, payment details и IP в открытом виде.
- IP логируется только как `HMAC-SHA256(ip, key)`, ключ в Vault, ротация раз в 30 дней. Простой SHA-256 не годится: всё пространство IPv4 перебирается за минуты.
- Пароли к БД, API-ключи и JWT secret хранятся только в ENV или HashiCorp Vault, никогда в коде или git.
- Для аналитики отдельная read-replica. Prod-БД доступна только с app-сервера.
- Бэкапы шифруются (age/gpg) и хранятся в отдельном регионе.
- PostgreSQL: только TLS-соединения, auth `scram-sha-256`.

**Защита от инъекций:**

- Только SQLAlchemy ORM, никакого raw SQL с конкатенацией.
- Pydantic strict mode для всех входящих данных.
- HTML-экранирование в чате сделок (защита от XSS, если бэкенд рендерит HTML).
- Валидация загружаемых файлов (receipts): проверка magic bytes, а не только MIME; re-encode через Pillow; лимит 5MB; только JPG/PNG/PDF.
- Загруженные файлы хранятся в отдельном S3/R2 bucket с pre-signed URLs (TTL 5 минут), НЕ на app-сервере.

**Защита от сетевых атак:**

- Cloudflare перед API: DDoS protection, WAF, Bot Fight Mode.
- **Origin закрыт от прямого доступа.** Основной вариант — Cloudflare Tunnel без открытых входящих портов. Если tunnel не используется:
  - порт 443 открыт только для IP-диапазонов Cloudflare (список обновляется автоматически);
  - включены Authenticated Origin Pulls (mTLS между Cloudflare и origin).
- Реальный IP origin нигде не публикуется: DNS-записи только proxied, исходящая почта идёт не с app-сервера.
- fail2ban на SSH + правила fail2ban на подозрительные паттерны API.
- SSH: только ключи, порт не 22, root login отключён, IP whitelist (или доступ только через VPN/bastion).
- Автоматические обновления безопасности (`unattended-upgrades`).
- Регулярный pentest / bug bounty (HackerOne, Immunefi).

### 7. P2P Trade Security

#### Escrow: состояния и таймауты

| Состояние | Что ожидается | Таймаут | Что происходит по таймауту |
|---|---|---|---|
| `LOCKED` | Продавец заблокировал крипту в escrow, сделка принята. Покупатель платит фиат и вызывает `markPaid` | окно оплаты из ордера: от 15 минут до 24 часов | **refund** продавцу |
| `PAID` | Покупатель отметил оплату. Продавец проверяет поступление и делает `release` или открывает спор | 24 часа | **auto-dispute**. Refund в этом состоянии невозможен |
| `DISPUTED` | Арбитр изучает доказательства и подписывает решение вместе с одной из сторон | 7 дней, затем эскалация к резервному арбитру | средства остаются в escrow и никогда не уходят автоматически |
| `RELEASED` / `REFUNDED` | — | — | финальные состояния |

- В любом нефинальном состоянии buyer + seller вместе (2 из 3 без арбитра) могут сделать release или refund.
- Переходы по таймауту выполняются контрактом: вызвать их может кто угодно, а результат определяется только состоянием и временем. Backend нужен лишь как удобный инициатор.
- Сделку по таймауту из `PAID` не может закрыть в свою пользу ни одна из сторон.

#### Защита от распространённых скамов

- **Fake payment confirmation.** Продавец сам вводит сумму полученного фиата, система сверяет её с ожидаемой. При расхождении автоматически открывается dispute.
- **Chargeback risk (обратимые методы: карты, некоторые банковские переводы).** Окно chargeback — недели и месяцы, поэтому защита строится на лимитах:
  - time-lock 30 минут на `release` после `markPaid` — против мгновенной отмены перевода;
  - продавец может разрешить обратимые методы только для покупателей с verified badge;
  - покупатель без verified badge при оплате обратимым методом ограничен суммой $100 за сделку и $300 в сутки;
  - в карточке ордера продавец видит, что метод оплаты обратим, и связанный с этим риск.
- **Social engineering в чате:**
  - фильтр внешних ссылок в сообщениях (разрешён whitelist);
  - детекция попыток увести общение в Telegram/WhatsApp, пользователь получает предупреждение;
  - изображения в чате проходят OCR: телефоны, номера карт и счетов, @username и ссылки, которые не совпадают с payment method ордера, блокируют отправку с объяснением.
- **Receipts** (чеки оплаты) загружаются только отдельной кнопкой «Прикрепить чек» в сделке, не через чат. На них нет OCR-запрета, но реквизиты получателя на чеке сверяются с payment method ордера; при расхождении продавец видит предупреждение.
- **Fake receipt images:** проверка EXIF, поиск по perceptual hash в базе ранее загруженных receipts. Совпадение с чужим чеком — автоматический dispute и флаг аккаунта.
- **Account takeover:** для сделок больше $500 обязательна 2FA. Одноразовый код приходит в Telegram от бота проекта (или через Telegram Gateway API) плюс биометрия в приложении. Код живёт 5 минут, даётся не больше 5 попыток. Код входа самого Telegram сторонним приложениям недоступен.
- **Sybil attack на репутацию:** verified badge минимум после 10 сделок с 5+ разными контрагентами. Детекция подозрительных паттернов: одно устройство и много аккаунтов (device fingerprint), сделки по кругу между одними и теми же аккаунтами.

#### Ограничения арбитра (на уровне контракта)

- Арбитр не может единолично сделать release: нужен мультисиг 2 из 3 (buyer ИЛИ seller + arbiter).
- Решение арбитра может отправить средства только buyer или seller сделки (или разделить между ними). На любой другой адрес, включая свой, перевод невозможен.
- Все действия арбитра логируются on-chain.

### 8. Supply Chain Security

- Сканирование зависимостей: `npm audit`, `pip-audit`, Dependabot, Snyk.
- **Сканирование секретов:** `gitleaks` в pre-commit и в CI (CI падает при находке), плюс GitHub secret scanning с push protection.
- **Утечка секрета:** если токен или ключ попал в git, он немедленно отзывается и перевыпускается. Удаления файла или переписывания истории недостаточно: секрет уже скомпрометирован.
- Lock-файлы в репозитории, воспроизводимые сборки.
- iOS: Swift Package Manager с закреплёнными версиями, никакого live-at-head.
- Android: Gradle version catalog, включён dependency verification.
- Backend: `pyproject.toml` с точными версиями, lock через `pip-compile --generate-hashes`.
- Docker images: только официальные базовые, закреплённые по digest (не по tag).
- Секреты CI/CD хранятся в GitHub Actions secrets / Vault, не в коде. Для деплоя используется OIDC, а не долгоживущие ключи.
- Подпись релизов (iOS автоматически, Android APK signing v2+).

### 9. Smart Contract Security

- **Внешний аудит до mainnet** (CertiK, Hacken, TonTech): $15–50k. Аудит нужен для каждого контракта отдельно: TON (FunC/Tact), Tron (Solidity/TVM), EVM (Solidity). EVM-контракт один на ETH и BSC, но конфигурация деплоя (адрес токена, decimals, лимиты) проверяется для каждой сети.
- Formal verification критичных функций (release, refund, resolve_dispute, переходы по таймауту).
- Bug bounty после запуска (Immunefi): минимум $50k за critical.
- **Pause:**
  - ставится мультисигом 3 из 5;
  - блокирует только создание новых сделок;
  - `release`, `refund`, переходы по таймауту, `dispute` и решения арбитра работают всегда, чтобы пауза не превращалась в заморозку чужих средств;
  - автоматически истекает через 72 часа, продление — новой транзакцией мультисига.
- **Лимиты в контракте:** в v1 максимум $10k на сделку. Значение задаётся для каждого токена в его единицах (см. «Правила работы с суммами»). Лимит повышается по мере тестирования через timelock 48 часов.
- **Работа с USDT:**
  - только через SafeERC20-обёртку: USDT ERC20 не возвращает `bool` из `transfer`/`approve`;
  - смена ненулевого allowance делается через сброс в 0;
  - фактически полученная сумма проверяется по разнице баланса escrow.
- Адреса токенов и decimals задаются в конструкторе и неизменяемы.
- Testnet-период минимум 2 месяца с реальными тестовыми сделками до mainnet.

### 10. Incident Response

- Статус-страница для даунтаймов (status.pmrwallet.com).
- **Аварийная кнопка «Снять все мои ордера»:**
  - приложение локально подписывает ключом пользователя сообщение отмены всех открытых ордеров с timestamp;
  - сообщение доставляется на backend; если основной API недоступен, — на резервный relay-эндпоинт;
  - backend и relay принимают его без JWT, только по проверке подписи. Поэтому кнопка работает, даже если аккаунт в приложении скомпрометирован или сессия отозвана;
  - активные сделки в escrow кнопка не затрагивает: их нельзя остановить односторонне, они идут по правилам раздела 7.
- Процедура disclosure: `security@pmrwallet.com` с PGP-ключом в `/.well-known/security.txt`.
- Попытки взлома логируются в SIEM (минимум Elasticsearch + Kibana) с алертами на всплески 401/403, срабатывания rate limit и несовпадения пинов.
- Регулярные бэкапы с ежемесячной проверкой восстановления.
- Runbook на случай утечки ключа (JWT secret, ключи шифрования PII, ключи мультисига): кто отзывает, в каком порядке, как уведомляются пользователи.

## Testing Requirements

Обязательные тесты для каждого критичного компонента.

**Validation tests:**

- Все известные форматы валидных адресов каждой сети → PASS.
- Невалидные адреса (длина, checksum, другая сеть) → REJECT.
- TON: testnet-адрес в mainnet → REJECT; raw `0:<hex>` → требует отдельного подтверждения.
- EVM: адрес в смешанном регистре с неверным EIP-55 → REJECT; адрес целиком в нижнем регистре → PASS.
- QR с chainId другой сети → REJECT.
- Fuzzing адресов (случайные байты) → никогда не падает.

**Network mismatch tests:**

- Адрес с активностью только в BSC при выбранной сети Ethereum → жёлтое предупреждение.
- Контракт только в Ethereum при выбранной BSC → красное предупреждение и повторный ввод суммы.
- RPC не ответил за таймаут → жёлтое предупреждение, не пропуск проверки.

**Amount / decimals tests:**

- `"1.5"` USDT_BEP20 → `1500000000000000000`; `"1.5"` USDT_TRC20/ERC20/TON → `1500000`.
- Ввод с большим числом знаков после запятой, чем decimals ассета → REJECT.
- Round-trip форматирования для каждого ассета из реестра без потери точности.

**E2E trade tests (на testnet, для каждого ассета маркетплейса, включая USDT_BEP20):**

- Happy path: order → accept → `markPaid` → release → review.
- Dispute path: order → accept → `markPaid` → dispute → решение арбитра.
- Timeout без оплаты: order → accept → окно оплаты истекло без `markPaid` → auto-refund продавцу.
